**Crop quality is the top priority, explicitly.** The user stated directly: getting a level, digit-only crop (via object tracking + rotation correction) is the most important part of the whole pipeline — a segment reader can't read reliably otherwise. Treat any crop regression as high priority, not cosmetic.

**Fully automatic only — no manual ROI clicking.** Explicitly rejected an interactive `cv2.selectROI` two-click flow in favor of automatic detection, even after being shown the accuracy trade-off (manual ~99% vs automatic ~87-98%) and choosing to keep automatic. Don't reintroduce a manual-selection step as the primary path.

**Always save debug images.** User wants `ocr_debug/` (captured + processed crops) written by default so they can visually check for problems themselves — don't pass `--no-debug` when processing videos for the user's actual review, only for quick internal test iterations.

**Scope discipline — don't reprocess videos the user didn't ask about.** When told to work on/fix something for one specific video, the user got frustrated when I proactively reprocessed the whole existing batch "for regression testing." Reason given directly: "eski videoları niye işliyorsun sadece yeni verdiğim video üzerinde çalış." How to apply: after a pipeline-wide change (e.g. a shared constant like `CROP_FRACTIONS`), it's fine to mention that old results are now stale, but don't rerun them without being asked.

**Keep outputs organized in dedicated folders, not the project root.** User asked to move working scripts/outputs into `nestle_syringie/`, and later asked for a further `deney_verileri/` folder specifically for analyzed (not raw) results. Default to creating a clearly-named subfolder for new categories of output rather than dropping files in the root.

**Ask before assuming a physical/scientific parameter.** Confirmed via AskUserQuestion before assuming liquid density (1.0 g/mL, water) for the mL-remaining calculation, rather than guessing. Apply the same standard to any other physically-consequential assumption (not just naming/formatting choices).

**Geometric auto-crop (rectangle/ring-based crop bounds) was tried and reverted — don't re-attempt without new evidence.** At the user's explicit request, tried deriving crop bounds directly from the bezel-border ring's detected interior (rotate level, re-find ring, inset past its thickness) instead of a fixed crop fraction. It worked well in isolated single-frame tests but was NOT robust across a full video: which preview frame the ring happened to be detected on materially changed the resulting crop (an occasional detection swept in an icon or the border edge itself as a false digit), and increasing the inset margin to compensate made things worse, not better (65%→53%→46% decode as margin increased). The working fix, agreed with the user: use the ring detection ONLY for the rotation angle (median across preview frames — more precise than the Hough-line fallback), and keep crop bounds on the fixed, tuned `CROP_FRACTIONS` constant. This hybrid got 96% on the video that prompted the investigation. If cropping quality becomes an issue again on a new dataset, the fix is very likely a `CROP_FRACTIONS` recalibration (see the manual grid-measurement process used earlier in this session), not another attempt at fully automatic per-video crop-bound derivation.

**Corrections happened in real time via direct inspection — trust the user's visual read of debug images over aggregate percentages.** Several "fixes" that raised the aggregate decode percentage were actually masking silent corruption (e.g. a morphological kernel that dropped digits silently rather than failing honestly) — this was only caught because the user kept asking to visually check specific `ocr_debug` frames rather than accepting the summary numbers. Keep offering/producing debug crops for spot-checking, and treat a decode-rate improvement with suspicion until a few actual frames are visually verified.

**No video-specific fixes — every fix must generalize, or it doesn't ship.** Stated explicitly and repeatedly once a second dataset (kıvampro) entered the picture: "video spesific çözüm üretmeni istemiyorum ... en azından verdiğim video seti için güvenilir veri üreten bir script olsun." When a bug is diagnosed on one clip, the fix has to be a general mechanism (wider search range, majority voting, a measured/justified threshold) applied uniformly, not a per-video lookup table or special-cased constant — even a single-entry `if video_key == "...":` override is out of bounds unless the user asks for exactly that (this DID happen once, deliberately, for two known-duplicate Nestle videos with the user's implicit go-ahead via the established pattern — but that was the exception being flagged, not the norm). How to apply: when a fix only works for the diagnosed video, keep iterating on the general mechanism (see [[project-lcd-pipeline]]'s ring-detection kernel-range/majority-vote and classify_digit g-segment-width history) rather than reaching for a per-video conditional, and validate every generalized fix against at least one *other* video (ideally a known-good one) before calling it done — several fixes in this session looked right on the target video but needed a second or third iteration once checked elsewhere (e.g. the spike filter's median window went 7 → 12 → 20 as denser/burstier noise patterns turned up on different videos).

**Don't trust an openpyxl-written Excel formula until it's actually been recalculated and (for anything chart-related) rendered to an image.** `openpyxl` only writes formula *text* — it never evaluates formulas, so reading a cell back with `data_only=True` right after writing returns nothing useful, and a formula that's syntactically fine can still be functionally wrong in ways that are invisible from the source (e.g. a `weight_kept_g` formula returning `""` for "excluded" rows parsed and saved without error, but Excel/LibreOffice's scatter chart engine plots `""` as `y=0` instead of skipping the point — only visible by actually looking at the rendered chart, not by reading formula strings or even recalculated cell values). Verification pattern that caught several real bugs this session: `soffice --headless --convert-to xlsx:"Calc MS Excel 2007 XML" --outdir ...` to force a real recalculation, then read the result with `openpyxl.load_workbook(..., data_only=True)` to check specific cells — and for anything about how a *chart* renders specifically, go one step further and `soffice --convert-to pdf` (with `ws.print_area` narrowed to just the chart's cell range and the other sheet(s) deleted from a throwaway copy, to avoid a 150-page PDF) then `pdftoppm` the page to PNG and actually look at it. Use a fresh `-env:UserInstallation=file:///tmp/...` profile dir per conversion to avoid LibreOffice's lock file/profile contention when running headless repeatedly.
